## 2. 模型类别输出（橘子 vs 橙子）

- **YOLO 把橘子输出为 `orange`**（COCO 类名），从未输出 "tangerine/mandarin"——COCO 没有该类别。这是**模型自己的类名，未做任何改标**。
- 数据真值（数据说明）是"橘子"。`orange` 在本数据集语境下应解读为"橘子（COCO: orange）"，B/C 使用时按数据集注释映射，不要混入"橙子"语义。
- 苹果输出 `apple`，无类别混淆。未出现其它水果类（banana 等）。
- 未发生"检测到水果 ≠ 需要特写"的越权判断：A 只给框和分数。

## 3. 竖屏方向 / 坐标问题（重要发现）

- 12 段视频容器编码为 2160×3840 且带 **rotation 元数据 = 90°**；OpenCV 默认**不应用**该元数据，直接 `capture.read()` 得到的是**横躺画面**。
- 实际正立画面 = 将解码帧**顺时针旋转 90°**，即 **3840×2160 横屏**。之前"竖屏 2160×3840"的预期与实际内容不符：手机录制时传感器方向导致存储为竖、显示为横。
- 已在 `run.py` / `downsample.py` 中加入 `--rotate auto`（按元数据自动旋转，也支持 cw/ccw/180/none 手动覆盖）。**JSONL 坐标全部基于旋转后的正立画面**，与 overlay 视频逐帧一致。
- 若 B/C 拿原始视频自行解码，必须做同样旋转，否则坐标错位。

## 4. 追踪稳定性

- 稳定案例：B01（全片各 1 个 ID）、A02（apple 1 / orange 2）、A03（orange 1）——静止桌面场景非常好。
- 碎片化案例：
  - **B03：apple 34 个 ID**。手持苹果近距离整理/推销，目标尺度和姿态剧烈变化，检测间歇丢失（低于 0.35）后 tracker 分配新 ID。
  - **C01：apple 26 个 ID**。特写阶段苹果占画面比例大、频繁出画/入画。
  - **C02/D01：25/115 个 ID**。多水果堆叠+遮挡。
  - 根因：`SimpleObjectTracker` 只做 IoU/中心距关联，`max_missed=8` 帧（约 0.27s），**无重识别**。短暂遮挡后必然换 ID。
- 结论：单目标静止/慢速场景 ID 稳定；手持特写和多实例遮挡场景 ID 不稳定，B/C 不能假设 track_id 跨遮挡持续。

## 5. 手部检测与手物关系

- MediaPipe Hands 在正立画面上工作良好：除 B02（353/398）外全部 ≥99% 帧有手，双手左右标签（hand_left/hand_right）正常。
- B02 低 45 帧：手在画面边缘快速移动时丢失，属正常。
- 已知局限：手离开画面中段时 MediaPipe 可能输出短暂漂移框；手持水果时手框与水果框重叠，relations 大量触发。
- relations：类型仅 `near_or_moving_together`（邻近/共同移动候选，含分数），**不是抓取、不是举起、更不是展示**。D01 中两只手同时对多水果产生多关系候选，属预期行为，需要 B 消歧。

## 6. 漏检 / 误检 / 遮挡案例

- 漏检：
  - A02 前 ~38 帧橘子未检出（远景小目标，conf<0.35）；A03 apple 288/447 帧（远景苹果偏小）。
  - **B02 orange 仅 116/398 帧**：橘子被挪入画面前不存在；挪入过程中运动模糊+手部遮挡导致间歇丢失（这是数据设计使然，不算模型失败，但 C 模块要能容忍目标晚出现）。
  - B02 手部 353/398 帧，画面边缘快速运动时丢手。
- 误检：未发现稳定误检（无椅子变苹果之类）。C01 的 orange 仅 8 帧，为远景橘子在画面边缘的零星检出，非持续误检。
- 遮挡：
  - C03（展示时短暂遮挡）：586/589 帧仍检出橘子，遮挡期间框有抖动、ID 有切换（10 个 ID），但整体连续。
  - C02/D01 水果堆叠：堆内水果互相遮挡产生大量短命 track；手持特写时手指遮挡水果下缘，框轻微收缩。
  - B03 手握苹果：苹果被手大面积遮挡时检测分数下降到阈值附近，造成 34 个 ID 的碎片化。

## 7. A 当前能支持的能力

1. 每帧（约 4 FPS 实时处理，非实时流）输出水果对象框（归一化坐标）+ 类别 + 置信度。
2. 稳定输出 `track_id`（静止/慢速单目标场景）。
3. 双手检测框与左右手标签。
4. hand–object 邻近候选关系（含分数），可作为 B 判断"拿起/展示"的证据之一。
5. 自动处理旋转元数据，坐标与正立画面对齐。
6. JSONL 契约校验工具（`validate_jsonl`）。

## 8. A 当前不能保证的能力

1. **不判断展示意图**——near 关系大量出现在"搬运/整理/双手放桌上"等非展示帧（B02/B03 即证明）。
2. track_id 跨遮挡不持续（无重识别）；手持特写场景 ID 会切换。
3. 远景小目标（ fruits 占比 <1% 时）会间歇漏检。
4. 处理速度 ~4 FPS（4K, imgsz=1280, RTX 4060），不适合实时直播场景；离线分析可用。
5. 类别受限于 COCO：橘子只能叫 `orange`，无法区分橙子/橘子/青柠。
6. 不输出遮挡标志、不输出 3D 深度、不输出"谁的手"（只有左右）。

## 9. 对 B 模块（展示意图）的接口建议

1. 展示证据组合建议：`hand–object near 关系持续 N 帧` + `对象框中心随手上移（bbox 中心 y 显著小于桌面基线）` + `对象框面积增大（靠近镜头）`。A 已提供全部所需原始量。
2. 不要按帧判定；建议 B 在 0.5–1s 滑窗上聚合 relations 与 bbox 轨迹。
3. 用 `class_name` 时把 `orange` 映射为数据集语义"橘子"，映射表放在 B 的配置里，不改 A 输出。
4. track_id 仅做短窗内关联键，勿跨长遮挡沿用；遮挡后可按"类别+位置邻近"重新关联。
5. conf=0.35 有间歇漏检，B 对"目标消失"应要求连续 N 帧缺失才认定消失。

## 10. 对 C 模块（自动取景）的接口建议

1. 特写目标框直接用 `objects[i].bbox_norm`，建议外扩 20–30% 裁切并平滑（bbox 每帧抖动明显，建议 EMA 或最小包围盒平滑）。
2. 目标切换（C02）：C 可根据"某 track 持续 near 手 + 位置移动向镜头"切换特写；A 不提供切换事件。
3. 遮挡/停顿（C03/C04）：目标短暂分数下降时不要立即切回全景——A 的框在遮挡后 1–2 帧内会恢复。
4. 多实例（D01）：同帧多个同类框，C 需要自己选主目标（例如离手最近/分数最高）；A 的 relations 分数可用于排序。
5. 注意坐标系：一切基于 3840×2160 正立画面；若 C 用原始视频帧，必须先做同样的 90° 顺时针旋转。

## 11. 本次对 A 模块代码的修改

修改前均已在对话中说明，修改后 `compileall` + `pytest`（3 passed）通过：

1. `src/perception/run.py`：
   - 修复手部框**双重归一化** bug（MediaPipe 已返回归一化坐标，之前又除以宽高 → 手框全为 [0,0,0,0]，并导致校验失败）。改为 clamp 到 [0,1]。
   - 新增 `--rotate auto|cw|ccw|180|none`：按容器 rotation 元数据自动旋转（本数据=顺时针 90°）。修复过程中又发现并修复 `cv2.ROTATE_90_CLOCKWISE==0` 被 `if rotation_code:` 吞掉的 bug（改用 None 表示不旋转）。
   - 新增 `--imgsz`（默认 1280）：640 输入下橘子漏检严重，1280 后置信度 0.65–0.9。
   - metrics 增加 `imgsz`、`rotation_applied`。
2. `src/perception/downsample.py`：同样加入自动旋转（否则降采样副本全是横躺画面）；输出尺寸改为跟随旋转后实际帧尺寸（`--width/--height` 不再决定输出方向）。

- 实际运行命令（每组一条，共 5 组；均为 `python -m src.perception.run --input ... --out outputs/perception_X.jsonl --overlay-out outputs/perception_X_overlay.mp4 --metrics-out outputs/perception_X_metrics.json` + `python -m src.perception.validate_jsonl ...`）。所有 JSONL 校验通过。

## 13. 是否需要降采样到 1080×1920

**建议：不需要。** GPU 上 4K 处理 3.7–4.6 FPS，12 段共 ~35 分钟即可全部跑完；降采样会损失远景小目标细节（橘子在 640 等效尺寸下已明显漏检）。若未来需要实时处理，建议优先降 imgsz 权衡或换更大模型+切片，而不是降采样副本（且副本应按旋转后 1920×1080 制作，不是 1080×1920——实际正立画面是横屏）。
